# konforme-ki.de — Astro static site

German-only, multi-page site for **konforme-ki.de**: an AI governance/inference product whose product is the exportable, hash-chained audit trail (*der Nachweis*), not the tokens.

**The brand is the domain, and "Nachweis" is a common noun — never a name.** Until 2026-08-26 `site.name` was `'Nachweis'` while the header read `konforme-ki.de` and the same word carried the value proposition in body copy ("Wir liefern beiden den Nachweis"), so a reader could not tell whether it meant the company or the proof trail. `site.name` is now `'konforme-ki.de'`; the noun survives everywhere and is the strongest word on the site. When writing copy: if the sentence needs a *subject that acts*, name the concrete thing (`Der Sidecar legt sich vor …`, `Der Router wählt …`) or the domain — never "Nachweis". Compounds (`Nachweis-Gateway`, `Nachweis-Metadaten`, `Nachweis-Rekord`) and the `#nachweis` section are noun usage and stay. `SeoHead` does **not** append `siteName` to `title` — it only feeds `og:site_name` — so each page's `| konforme-ki.de` suffix is hardcoded in its own `title` const and a brand change means sweeping them. Target audience is broad — any EU company with a Datenschutzbeauftragter or Betriebsrat blocking an AI rollout (Art. 28 DSGVO, US CLOUD Act/GeschGehG, §87 Abs. 1 Nr. 6 BetrVG) — with Berufsgeheimnisträger under § 203 StGB (Steuerberatung, Rechtsanwaltschaft, Arzt-/Zahnarztpraxen, Notariate, Psychotherapie, Pflegedienste) kept as a named, still-served niche rather than the whole pitch.

**As of 2026-08-26, three equally-ranked products replace the old Sidecar-first framing**: `Deutschland-Inferenz` (own German hardware, highest protection grade — `de-only`), `Router` (one OpenAI-compatible endpoint, four selectable protection grades, backed by an OpenRouter-based gateway), and `Sidecar` (same compliance layer in front of a customer's *existing* Azure OpenAI/Bedrock/own cloud, zero migration). All three deliver the **same underlying grade system** from `openrouter-sidecar-compliance/README.md`'s "Policy presets" — see `src/lib/stufen.ts`. The **first CTA site-wide is the `/einstufung` questionnaire**, not any single product — it recommends a product + grade + document list in four questions, entirely client-side (`empfehleStufe()` in `src/lib/einstufung.ts` is a pure function, no backend). Read `MARKETING.md`'s top section (the 2026-08-26 rephrase brief) before reverting this — the older "Sidecar is the primary offer" framing further down in `MARKETING.md` is now superseded by it, kept for its still-valid reasoning on audience breadth and vertical prioritization. Astro 7 + Tailwind v4 (Vite plugin, no `tailwind.config`), static output, deployed to GitHub Pages.

**The quiz never states which law applies to a visitor** — `rdg-hinweis.md` explicitly disclaims giving legal assessments, so `empfehleStufe()`'s output is always phrased as a product/grade recommendation plus a document checklist, never as "§ 203 StGB applies to you". Don't loosen this wording.

Business context and the funnel design live in `MARKETING.md` at the repo root (there is deliberately **no README** — `MARKETING.md` is the canonical business-context doc) — read it before making content changes. Paid-acquisition copy lives in `ADS.md`: six Meta campaigns with targeting keywords, headlines, primary texts, image prompts and the Meta-safety scrub. **Any claim added to an ad must already be true on the page it links to** — `ADS.md`'s claims are drawn from `stufen.ts`, `produkte.ts` and `preise.ts`, never invented for the ad. Its **"The selling points, in the order a visitor meets them"** section is the canonical list of what the homepage must keep doing; weakening one of those nine is a regression, not a redesign.

## The shared plumbing layer: `@justinguese/astro-kit`

This site is migrated onto `@justinguese/astro-kit` v0.4.0 (npm, `~/code/websites/datafortress-astro-kit`), the shared "invisible correctness layer" also used by pruefanfrage.de: consent-gated analytics, first-touch attribution, SEO head, funnel/conversion tracking, prose CSS, role tokens, and a growing set of section blocks — `HeroBlock`, `ScarcityBlock`, `PricingCards`, `FaqBlock`, `FormBlock`, `SectionHeader`, `CtaBand`, `ProofBlock`, `ArticleLayout`, `ArticleGrid`, `Breadcrumbs`, `ReadingProgress`. **Read the kit's own `AGENTS.md` before touching consent, tracking, forms, the `@theme` tokens in `global.css`, or any of these blocks** — it documents the paired contracts (`CookieBanner`↔`Consent`, `Attribution`↔`TrackingFields`, `FormBlock`↔`ConversionTracking`), the migration playbook (visible-text diffing technique), and the hard rules (no color literals outside the site's own `@theme` block, never add `@source` for the kit).

A caret range on the kit's `0.x` version locks the MINOR — `^0.4.0` will not accept `0.5.0`. Bumping to a new kit minor needs `package.json` edited by hand, `npm install`, then a rebuild + `astro check` + visible-text diff, same as any migration step. `CompareBlock` is adopted on `/deutschland-inferenz` (comparing against OpenAI/Anthropic/Google/Azure on jurisdiction facts only, never capability or price — see `src/lib/deutschlandInferenz.ts`'s header comment for why).

**`SectionHeader`'s `title`/`lead` are plain-string props, not slots** (unlike `HeroBlock`'s `headline`). Any section whose heading or lead paragraph needs inline markup — a colored `<span>`, a `<strong>`, a `<code>` — cannot use it without losing that emphasis. `#nachweis` and `#checkliste` on the homepage, and the h1 on `/integrationen` and `/playground`, are left as hand-written headers for exactly this reason. Don't "finish the sweep" on those without re-solving that problem first.

What stayed local, deliberately, and why (don't "finish the migration" by moving these — they were evaluated and kept):
- **`LeiterTabelle.astro`** (the homepage offer ladder) — the kit's `PricingCards`/`Tier` type has no field for `eignung` (audience-fit sentence per tier) or `nummer` (ledger numbering), and the `ANKER` price-anchor panel is fused into the same component.
- **`ZugangForm.astro`** — its `_next` redirect value and submit-button label both change client-side after reading `?tarif=`, which the kit's `FormBlock` has no hook for (single computed `_next`, static `submitLabel`). It still uses the kit's `TrackingFields` directly.
- **`Kette.astro`** (the hash-chain rail), **`RekordKarte.astro`**, **`Playground.astro`** — these are the site's own identity, not plumbing; the kit's `AGENTS.md` explicitly calls out the hash-chain as a "stays in its site" example. `Kette.astro`'s `.kette-strich` also duplicates the kit's `ReadingProgress` — kept local because it's already branded into the `Kette` identity, not swapped.
- **`Belege.astro`**'s stat cards — adopted the kit's `ProofBlock` (stats-only, no quotes — see below), but overrode its default dark `--color-premium-bright` card styling via a local `.belege-hell` class in `global.css`, since this site reserves premium exclusively for Säule 3 and the section sits on a light background. The override, not the block itself, is what's local here.
- **`src/pages/unterlagen/[slug].astro`** — not moved onto `ArticleLayout`. It's a printable reference document (own `.druck-kopf` print header, "Als PDF drucken" button), not a long-form article; `ArticleLayout`'s breadcrumbs/TOC/related furniture don't fit that use case the way they do `ratgeber/[slug].astro`.

`ProofBlock`'s `quotes` are unused on purpose: `Belege.astro` passes `stats` only. The section's own headline — "Wir zitieren keine Kunden, die wir noch nicht haben" — is a deliberate no-quotes stance (see the § 5 UWG note in `belege.ts`), not a placeholder waiting to be filled in. If real testimonials are ever added, use `ProofBlock`'s `quotes` prop with `unverified` unset (only while genuinely unverified) — never invent one to fill the block's shape.

## Structure

- `src/pages/index.astro` — homepage, 12 chained sections ordered by **funnel logic, not product logic**: `hero` → `problem` → `werkzeuge` → `lock-in` → `playground` → `nachweis` → `unterlagen` → `checkliste` → `leiter` → `zugang` → `faq` → `abschluss`. There is no `produkte` section — the three products live *inside* `hero` as `ProduktDreieck`, which is the point of the 2026-08-26 rephrase. Keep the disclaimers and off-page links **after** `zugang` — in front of the form they cost conversions. Uses the kit's `ScarcityBlock`, `FaqBlock`, `CtaBand`, and `SectionHeader` on every section opener except `#hero`/`#nachweis`/`#checkliste` (inline `<span>` in the heading — see above). The hero is hand-written, **not** the kit's `HeroBlock`: it is a two-column grid (pitch left, `base_url`-diff right) and its H1 carries an inline `<span class="text-accent">`.
  - The hero must keep naming the category outright ("OpenAI-kompatible KI-Schnittstelle") and showing the `base_url` swap. Before 2026-08-26 the first viewport contained neither, so a cold visitor could not tell an API from a consultancy, and the cheapest-switching-cost argument sat three sections down. `heroWechsel` builds its URL from `apiUrl()` so the hero and `WERKZEUGE` cannot drift.
  - **One CTA string site-wide: „Passende Stufe finden."** Header, sticky bar, hero, `/router` and the closing band all point at `/einstufung` — a different label per placement spends six impressions without compounding recognition.
  - **Never describe the quiz as taking five minutes.** It is four radio questions; "5 Minuten" manufactured friction against a ~60-second form. Copy says `Vier Fragen · 60 Sekunden`.
- `src/pages/einstufung.astro` — the first CTA site-wide. Renders `Einstufung.astro`, a four-question form whose submit handler imports `empfehleStufe()` directly (Astro bundles the `<script>` module) and renders the result client-side — no server round-trip, because the site is static. `<noscript>` links straight to all three product pages so a JS-less visitor isn't stranded. The page carries its own `ConversionTracking` for the `einstufung_gesendet` flag.
  - **The result is never gated.** The email form sits *below* the fully rendered recommendation — an offer, not a toll, consistent with the ungated Unterlagen. Don't turn it into a gate to lift capture rate.
  - The kit's `FormBlock` is an Astro component and the result panel is built with `innerHTML`, so the form **cannot** be rendered into the result string. It is server-rendered hidden below the panel; `renderErgebnis()` unhides it and fills the hidden `produkt`/`stufe`/`unterlagen` inputs, so a Formspree submission carries the recommendation it refers to rather than a bare address.
- `src/pages/router.astro`, `sidecar.astro` — the other two products, matching `/deutschland-inferenz`'s depth (grade table, fail-closed explanation, `WerkzeugTabs`, pricing-logic paragraph — no invented numbers). `/router` also carries the 103-provider jurisdiction table from `openrouter-sidecar-compliance/README.md` and a short vendor-lock-in section (swap the provider behind the endpoint, tools pointed at the `base_url` don't need reconfiguring).
- `src/pages/playground.astro` — full scripted playground (see below). Its h1's lead has an inline `<strong>`, so the header stays hand-written.
- `src/pages/integrationen.astro`, `eu-ki-recht.astro`, `preise.astro` — secondary content pages. `/preise` uses the kit's `PricingCards` + `SectionHeader`. `/integrationen`'s h1 stays hand-written (inline `<code>` in the lead); it now renders `WerkzeugTabs` instead of a local `codeTabs` array, and its Säulen section notes how Säule 1/2/3 map onto the four grades in `stufen.ts`.
- `src/pages/unterlagen/index.astro` + `[slug].astro` — the ungated lead magnet, rendering `src/content/unterlagen/*.md` (its own local schema — no kit equivalent). The index page's listing uses the kit's `ArticleGrid` + `SectionHeader`; `[slug].astro` keeps its own print-focused template (not `ArticleLayout` — see below).
- `src/pages/ratgeber/index.astro` + `[slug].astro` — SEO articles from `src/content/ratgeber/*.md`, grouped by `category`. The index page's listing uses `ArticleGrid` + `SectionHeader`. `[slug].astro` uses the kit's `ArticleLayout` (breadcrumbs, sticky TOC, header, body, disclaimer slot, `ArtikelUpsell.astro` in the cta slot, related-articles via `ArticleGrid`) — `progress={false}` since the site's own `kette-strich` bar already covers that. No article currently sets `faq` frontmatter, so `ArticleLayout`'s FAQ section never renders; don't invent Q&A to fill it (see "Articles must not invent facts" below).
- `src/pages/[slug].astro` — single dynamic route rendering `src/content/legal/*.md` (impressum, datenschutz, agb, rdg-hinweis). Don't recreate the old one-file-per-page wrappers.
- `src/pages/kontakt.astro` — secondary contact form, reached via `?interesse=onboarding|sidecar|compliance`. Uses the kit's `FormBlock` + `ConversionTracking`.
- `src/layouts/Site.astro` — shared shell built on the kit's `SeoHead`, `Consent`, `CookieBanner`, `StickyCta`, `Attribution` and `FunnelTracking` (see the kit's `AGENTS.md` for what each does). The sticky mobile bar targets `/?tarif=compliance#zugang`, not `/playground`. Also owns the `kette-strich` mobile progress line and the nav `<details>` menu, which stay site-local.
- `src/config/site.ts` — the one place brand name, address, GA4/Meta Pixel IDs and the Formspree id live (`defineSiteConfig`). All public by design; never put a secret here.
- `src/lib/kette.ts` — build-time hash chain for the `Kette` (chain rail) signature element. Real sha256, not decorative.
- `src/lib/playground/{types,script,transport}.ts` — the playground's swappable transport. `scriptedTransport` (default, no backend) vs. `httpTransport` (used automatically once `PUBLIC_GATEWAY_URL` is set). Don't hardcode which one runs — always go through `getTransport()`.
- `src/lib/preise.ts` — single source of truth for pricing. Two distinct things: `LEITER` + `ANKER` (the **offer ladder** — €0 checklist / €39 dossier / €290 compliance, plus the €1,900–9,000 anchor; rendered by `LeiterTabelle.astro` on the homepage, kept local) and `NUTZUNGSMODELLE`/`SERVICE_TARIFE` (**billing models**, rendered by the kit's `PricingCards` on `/preise` via the `tarifAlsTier()` adapter in this file). The ladder is the buying decision; the token tiers are a billing detail — don't merge them back into one table on the homepage. Field names stay German (`tarifId`, `preis`, `einheit`, …) throughout — `ZugangForm.astro` loops over `LEITER`+`ANKER`+`NUTZUNGSMODELLE` together assuming one shared shape, so don't rename fields on just one of them.
- `src/lib/belege.ts` — social proof. `Belege.astro` renders `SIEGEL`, four factual claims (not testimonials). **If this ever grows a quote/testimonial list, invented ones are unlawful in Germany (§ 5 UWG)** — use only released quotes.
- `src/lib/kontingent.ts` — the scarcity numbers (monthly access-key quota), rendered via the kit's `ScarcityBlock` (wrapped in a local `.kontingent-akzent` class — see `global.css` — so it renders in this site's accent color rather than the kit's default `--color-signal`, which on this site means exclusively "fail closed"). Real, because keys genuinely are issued manually; bump `vergeben` after each round. Never turn this into an auto-incrementing fake counter.
- `src/lib/stufen.ts` — the four protection grades (`de-only`/`eea-region`/`eu`/`global-audited`), copied from `openrouter-sidecar-compliance/README.md`'s "Policy presets" table, not invented here. Each grade's `caveats` field is what it does NOT achieve — always render it alongside the grade, never just the promise. `de-only` carries `nurEigeneHardware: true`: it is the one grade no gateway can deliver, so `/sidecar` and `/router` must never claim it, only `/deutschland-inferenz`.
- `src/lib/produkte.ts` — the three products (Deutschland-Inferenz/Router/Sidecar), each declaring which grades it can actually deliver. Feeds `ProduktDreieck.astro`, the header's Produkte dropdown, and the footer. **Every number in `kosten` has a counterpart in `preise.ts`** (`pay-per-token` €3,50/Mio., `compliance` €290/Monat) — never invent a price here, or the homepage and `/preise` drift. The three products genuinely bill in different units; `kostenZusatz` carries that nuance so the cards stay comparable instead of being forced into one false unit. `cta` is rendered by `ProduktDreieck` as the card's primary action — it was dead data until 2026-08-26, which cost three product-specific conversion paths.
- `src/lib/einstufung.ts` — the quiz questions and the pure `empfehleStufe()` scoring function. Keep it side-effect-free and DOM-free so every answer combination stays independently testable.
- `src/lib/werkzeuge.ts` — the tool-swap tabs (`WerkzeugTabs.astro`). Each entry carries a `status` field like `KanalKarte`'s. `claude-code` was promoted to `verfuegbar` on 2026-08-26 against a live `POST /v1/messages` (structured `invalid_api_key`, not a 404 — the shim runs); the dated note in the file header is the evidence, and any future promotion needs the same. **`copilot` is the one entry promoted on the operator's say-so without an own check** — its mechanism belongs to a third party (Copilot Chat's own model binding in VS Code), so the file header carries an OPEN marker to click through once and replace with a dated confirmation.

## Conventions

- **No i18n.** The site is German-only (`lang="de"` hardcoded). Don't reintroduce locale routing.
- **Lead capture and checkout run on our own funnel API** (`~/code/shared-marketing-email-ecommerce-endpoint`, deployed at `ecommerce-api.datafortress.cloud`), not Formspree. `site.formsBase` in `src/config/site.ts` is the one switch; `formspreeId` stays only as a fallback for a form that does not pass `formsBase` through. Four forms, distinguished by the URL's last segment rather than by a hidden field: `kontakt`, `zugang` (waitlist + access requests), `infografik` (PDF checklist gate, on both `/` and `/eu-ki-recht` via `quelle`/`id` props so the two instances stay distinguishable in the id-prefixed DOM), `einstufung`. Which Meta event each one fires is configured **server-side** in that repo's `sites.yaml`, not here — `infografik` fires `FreeDownload`, deliberately not `Lead`.
  - **The endpoint answers a form POST with a 303 to `_next`.** That redirect is the only reason `ConversionTracking` fires. If forms start working while conversions stop being counted, check that first.
  - Success handling is the kit's `ConversionTracking` (analytics + URL cleanup) plus a small per-form local script (reveal/hide the DOM panels) — bypassable by hand-editing the URL; accepted limitation of the static-site approach.
  - `PUBLIC_FORMS_BASE` overrides `formsBase` at build time, so `npm run dev` can point at a funnel API on localhost instead of creating real submissions.
- **Every offer CTA must be attributable.** Content CTAs carry `data-cta="<tarifId>"`, picked up by the kit's `FunnelTracking` (fires `cta_click` with `{cta: label}` — one event name, the label as a parameter, never `${tarif}_cta_click`). Links additionally go through `zugangHref(tarifId)` → `/?tarif=<id>#zugang`; `ZugangForm.astro` reads the param into hidden `tarif`/`tarif_klartext` fields and adapts its submit label. Without this, all CTAs land in the notification inbox indistinguishable from each other. New offers get a `tarifId` in `preise.ts` — never a bare `/#zugang` link. Purchasable tarifs instead go through `kaufHref(produktKey)` → `/kasse?produkt=<key>`, which starts a Stripe Checkout Session via the funnel API.
- **DataFortress.cloud GmbH is the face of the product, not an EU third party.** `STANDARD_SAEULE` in `src/lib/saeulen.ts` (= Säule 2, own infrastructure in **Nürnberg**, no external subprocessor) drives the playground's preselected pillar and the example records on the homepage. Never put a third-party provider name (Mistral, IONOS, …) in the hero or the primary `RekordKarte` — a foreign vendor name in the showcase record raises exactly the question the product exists to answer. Säule 1 stays selectable and is named in the pricing and FAQ.
- **No hardcoded dates in anything time-sensitive.** The site is statically built and not rebuilt per visit, so a compiled-in month or date is wrong within weeks. Scarcity copy uses relative wording only ("diesen Monat", "pro Monat") — see `src/lib/kontingent.ts`. The playground's recorded records get their `zeitstempel` stamped with `new Date()` at playback (`mitJetztStempel` in `transport.ts`). If you ever need a concrete date on screen, generate it client-side. `Stand:`/`updated:` version dates on legal texts, Unterlagen and Ratgeber articles are the deliberate exception — they document when content was last reviewed and must stay.
- **The playground never fakes being live inference without saying so.** Every instance of `<Playground />` must show the "Demo · aufgezeichnete Antworten, keine Live-Inferenz" label. Don't invent latency/throughput numbers.
- **Consent Mode v2 is load-bearing, not decorative.** GA4/Meta Pixel must stay `denied` by default and only fire after `cookie-consent-updated` (accepted) — handled by the kit's `Consent`/`CookieBanner` pair now. A compliance product that tracks before consent is a credibility bug, not a minor one — don't regress `Site.astro`'s consent gating when touching analytics. Verify with a real browser in an isolated context (fresh visitor, accept, reload-after-accept, decline-then-reload, and the footer's `data-consent-reopen` button), never by reading the code — see the kit's `AGENTS.md` for the exact checks.
- **GA4/Meta Pixel IDs and the API hostnames live in `src/config/site.ts`** (public by design — they compile into static HTML). Two hosts, deliberately separate: `API_HOST` (`api.konforme-ki.de`) is the *inference* endpoint printed in the copy-paste code samples in `werkzeuge.ts`; `MARKETING_HOST` (`ecommerce-api.datafortress.cloud`) is forms, lists and checkout. `PUBLIC_GATEWAY_URL` and `PUBLIC_FORMS_BASE` are the only env vars (see `.env.example`), injected via `env:` in `.github/workflows/deploy.yml`.
- **SEO articles (`src/content/ratgeber/`) follow a fixed recipe**: minimum 1200 words, 9-13 short `##` sections, no `#` H1 (the template renders `title`), and **no closing CTA in the markdown** — `ArtikelUpsell.astro` renders it. Every article ends on a bridge paragraph about the gap between being compliant and being able to prove it. `metaTitle` is keyword-first and may differ from `title`; `description` stays at 150-158 characters. `updated` is a real ISO date (`2026-08-07`, quoted or not — the kit's schema accepts both YAML spellings) — it feeds JSON-LD `dateModified` and `<meta property="article:modified_time">` directly, so don't put a German-formatted string there; the display format on the page comes from `formatDeDatum()` in `src/lib/format.ts`.
- **Articles must not invent facts.** No customer names, testimonials, statistics, percentages, court rulings, Bußgeld amounts, or benchmark numbers. **Regulatory dates come only from `eu-ki-recht.astro`** — it is the single source of truth for the AI Act timeline (including the Digital Omnibus shift of Annex III to 2. Dezember 2027) and the DPF status. Never recall a date from memory. Discuss competitors as categories and patterns, never with specific factual accusations.
- **Markdown tables scroll themselves.** `.article-body` structure comes from the kit's `styles/prose.css`, but its default table is `width: 100%` with a `min-width` per cell — that reintroduces page-level horizontal scroll on this site (a real regression that happened once already), so `global.css` overrides `.article-body table`/`td` back to `width: max-content` / `max-width: 100%` / no `min-width`, right after the kit import. Never remove that override or add `min-width` back.
- **Legal and regulatory accuracy matters here.** `datenschutz.md`, `agb.md`, `rdg-hinweis.md`, everything in `src/content/unterlagen/`, and `eu-ki-recht.astro` are legal/regulatory content, not marketing copy — flag material changes rather than silently editing. Regulatory dates (AI Act, DSGVO) must be verified against a current source before writing, not recalled from memory; see the `Stand:` date on `eu-ki-recht.astro`.
- **Never claim an unshipped integration, customer, or metric.** `KanalKarte` status badges must reflect reality — default to `in-vorbereitung`/`auf-anfrage`, not `verfuegbar`, unless it's actually live. As of 2026-08-26 every channel on `/integrationen` is `verfuegbar` on the operator's confirmation; the rule is unchanged, only the current values are. The homepage's own `kanaele` badge row renders no status at all, so it is only honest while every channel it names is live — if any one regresses, that row must gain a status or drop the channel.
- **URL renames need a redirect; GitHub Pages has no server to do it.** `astro.config.mjs`'s `redirects` map emits a static meta-refresh page with a canonical link (`/eu-inferenz` → `/deutschland-inferenz`, 2026-08-26). Add the old path to `sitemapConfig`'s `exclude` in the same edit so the stub isn't indexed next to its target.
- **Two upstream mechanisms coexist — don't conflate them.** `NUTZUNGSMODELLE`'s Säule 1 (pay-per-token/chat/pro on `/preise`) uses a fixed, EU-only 4-provider list — Scaleway, IONOS AI Model Hub, Mistral AI, OVHcloud AI Endpoints — with no OpenRouter involvement; keep that claim absolute there. **`Router`/`Sidecar` (the grade system in `stufen.ts`) run on an OpenRouter-based gateway** (`openrouter-sidecar-compliance`) and may name it openly — the 103-provider jurisdiction table (54 US-HQ, 29 unknown, 4 EEA-HQ) is the strongest asset on `/router`, not something to hide. The site-wide promise is **"nie unterhalb Ihrer gewählten Schutzstufe"** (fail-closed per grade), not a blanket "no US fallback" — only `de-only`/Deutschland-Inferenz still carries the absolute EU-only claim, because it's the one grade with no gateway involved at all.

## Deploy

GitHub Actions → GitHub Pages (`.github/workflows/deploy.yml`, `withastro/action@v6`), triggered on push to `main`. `PUBLIC_GATEWAY_URL` is injected from a repo secret at build time; everything else (form endpoint, GA4, Meta Pixel) is committed in `src/config/site.ts`, not a deploy-time secret.
